# AGENT:24 — 파이프라인 기술 스펙 (확정: 6.5단계)

관련 문서: `01_전략_기획.md`(왜 이 구조인가) · `03_실행계획.md`(누가 언제 만드는가)

## 확정 파이프라인

### 0. Scope Calibrator — OpenAI (Agents SDK)
입력 주제의 범위를 판정한다.
- 너무 넓으면 하위 기술 3~5개로 자동 분해
- 너무 좁으면 상위 개념/인접 키워드로 확장
- 가짜/존재하지 않는 개념이면 탐색 후 조기 종료
- 사용자에게 재질문하지 않고 대표 범위를 스스로 선택 (자율성 규칙 준수)

### 1. Scholar Scout — Liner Search API (Scholar)
하위 기술별로 메타분석·재현연구·현장실험·반박연구·최신연구를 탐색한다.
출력: "검증됨"이 아니라 "근거 성숙도 82/100" (Evidence Maturity)
- 신호: 반복 검증 정도 / 연구자·기관 독립성 / 결과 방향 일관성 / 현실 환경 검증 여부 / 최근 반례 존재 여부
- **점수 계산 방식(방어 가능하게)**: LLM이 홀리스틱하게 "몇 점"으로 채점하지 않는다. 신호별로 이산적으로 세서(독립 출처 개수, 재현연구 존재 여부(0/1), 최근 반례 개수 등) 가중합으로 82를 만든다. "왜 82인가"를 신호별 카운트+가중치로 바로 설명할 수 있어야 한다. LLM의 역할은 "이 논문이 재현연구인가/반례인가"를 판별하는 이산적 신호 추출로 한정한다.

### 1.5. Vocabulary Bridge — OpenAI (Scholar Scout와 Adoption Scout 사이)
학술 용어를 그대로 산업 검색에 쓰면 안 된다 — 학계는 "gradient boosted decision trees", 업계는 "XGBoost"처럼 같은 기술을 다른 이름으로 부르는 경우가 흔하다. 이 다리가 없으면 실제로는 채택된 기술도 전부 "적용 갭"으로 오판하게 되어 3점수 분리 체계의 전제가 흔들린다.
- Scholar Scout에서 나온 학술 용어를 받아 업계 동의어 후보 2~3개 생성 (예: "gradient boosted decision trees" → "XGBoost", "LightGBM", "gradient boosting")
- 이 동의어 전부로 다음 단계(Adoption Scout)의 산업 검색을 수행
- 새 API 호출이 아니라 프롬프트 단계로 처리 (파이프라인 번호 재조정 불필요)
- **매핑 신뢰도를 Coverage Confidence에 반영**: 업계 표준 명칭이 명확한 경우와 확신 없는 직역 수준 매핑인 경우를 구분해서, 후자는 Coverage Confidence를 낮춘다

### 2. Adoption Scout — Liner Search API (Web)
Vocabulary Bridge에서 나온 학술 용어 + 업계 동의어 후보 전체로 산업 측 검색 (제품문서, 사례연구, 표준/지침, 오픈소스, 채용공고, 조달사례, 산업보고서).
출력: "사용되지 않음"이 아니라 "공개적으로 확인 가능한 도입 증거가 제한적임 (검색범위: N개 신호군, M개 결과)"
- **점수 계산 방식**: Adoption Evidence도 동일하게 "신호군 몇 개 중 몇 개 확인"으로 이산적 카운트 후 가중합. 홀리스틱 LLM 채점 지양.

### 3. Gap Candidate Generator — OpenAI
3개 점수를 분리해서 산출한다:

| 점수 | 의미 |
|---|---|
| Evidence Maturity | 연구 결과가 얼마나 성숙했는가 |
| Adoption Evidence | 현실 도입 증거가 얼마나 확인되는가 |
| Coverage Confidence | 검색 범위가 결론 내리기에 충분한가 |

"성숙도 높음 + 도입 증거 낮음"만으로 갭을 선언하지 않는다. 커버리지까지 충분해야 강한 후보로 승격한다.

### 4. Adversarial Verifier — Liner Search Agent API
상위 후보마다 반대 질의를 수행한다: "이 기술이 산업에서 이미 널리 쓰인다는 증거를 찾아라." 검색 부재를 현실 부재로 오인하는 문제를 완화한다.
- **실측 확인**: `mode` 필드로 학계/산업 반증 질의를 파라미터 하나로 구분 가능 (`mode: "scholar"` / `mode: "general"`) — 별도로 Web/Scholar를 나눠 호출할 필요 없이 이 필드로 처리
- 인용 근거는 `data-search-chunks` 이벤트의 `referenceChunks[]`(num, content, sourceTitle, sourceUrl)를 그대로 반증 근거 로그(`counter_evidence_log`)에 매핑
- 단일 반증 질의로 단순화한 것은 시간 제약을 고려한 **의식적 선택**이다 (엄밀히는 후보마다 여러 각도에서 공격하는 게 더 견고하지만 24시간 제약상 단순화)
- 여유 있으면(필수 아님): 후보의 잠재 임팩트에 따라 반증 시도 횟수를 가변화 (고임팩트 후보는 2회, 나머지는 1회)

### 5. Conditional Deep Research — Liner Deep Research Agent API
**기본 엔진이 아니라 최종 감사관.** 다음 조건에서만 승급:
- 학술 결과 상호 충돌
- 산업 도입 증거 모순
- 임팩트는 큰데 확신도 낮음
- 상위 1개 후보의 원인까지 조사 필요

**실측 결과 (중요)**: 단순 질의 1건 기준 실제 소요시간 ~59초. 최초 가정(15~20초)의 3배 이상.

**타임아웃 전략 (확정)**
- 서프라이즈 태스크: 짧은 타임아웃 유지(20~25초) → 강등(fallback)을 **의도된 기본 시나리오**로 채택한다. 소요시간을 예측할 수 없는 입력이므로 발표 시간의 통제권을 우리 쪽에 남겨둔다. "느릴 수 있다는 걸 알고 이렇게 설계했다"는 스토리 자체가 Real-time Adaptability 25%를 증명하는 방법이다.
- 사전 리허설된 안전 데모 입력: 예외적으로 타임아웃을 늘려(예: 70초) Deep Research 성공 경로를 라이브에서 직접 시연한다. 대기 시간엔 "왜 이 단계가 필요한지" 나레이션으로 채워 죽은 시간이 없게 구성한다.
- 타임아웃 미완료 시 → 지금까지의 Search Agent 근거로 잠정 결론 + 확신도 낮음 표시하고 진행
- 대기 중에도 SSE 스트림의 중간 이벤트를 화면에 계속 노출 (로딩이 아니라 "일하는 걸 지켜보는 시간"으로 전환)

**실측 결과**: 이벤트 순서가 문서와 다르다. 문서상 "사고 먼저 → 답변"이 아니라 실제로는 **"답변 먼저(text-start/delta/end) → 사고 요약 나중(reasoning-delta 통째로 한 번 더) → reasoning-end → finish"** 순서로 온다. UI에서 "생각 중 패널"을 답변보다 앞에 두려던 설계는 순서를 뒤집어야 한다 (오히려 답변이 먼저 뜨는 게 반응성이 좋아 보여서 데모엔 유리할 수 있다).

**문서에 없는 이벤트 다수 존재 — fallback 처리 필수**: `query_classification`, `data-search-decision`, `data-rich-content`, `data-quickanswer-queries`, `data-highlight-phrases`, `data-follow-up-questions` 등. Raw API Stream 화면은 unknown event type이 와도 깨지지 않고 최소 로그로라도 노출되게 구현한다 (오히려 "가공 없이 노출"이라는 규칙 취지에 더 맞는다).

### 6. Gap Map — Liner Visualization API
목표 화면 예시 (스케치, 실제 렌더링 결과와 다를 수 있음 — 아래 리스크 참고):
```
연구 근거 성숙도 ────────── 88
공개 도입 증거   ────────── 24
검색 커버리지    ────────── 81

적용 갭 신뢰도: HIGH

확인된 장벽
• 기존 인프라와의 통합 비용
• 규제 승인 부족

추론된 장벽
• 현업 인지도 부족
```

**실측 확인: 완전 자유 커스텀 아님.** 응답은 완전한 HTML 문서(`atlasArtifact.html`)가 SSE로 오고, `iframe srcdoc`에 주입하는 구조다. `theme` 필드가 10종(`comparison, hierarchy, process, trend_analysis, summary, distribution, explainer, calculator, game, instrument`) 중 하나로 자연어 쿼리 기반 자동 선택되며, 위 스케치 그대로 나온다는 보장은 없다 (`comparison` 또는 `summary`에 가까울 것으로 예상, 실측 필요).
**응답 시간 (문서 명시): 평균 20~30초** (Web Search + 렌더링 포함) — Deep Research 없이도 파이프라인 총 소요시간에 이미 20~30초가 더해진다. 데모 시간 예산 재계산 시 이 값을 반드시 반영한다.
`is_search_context: true` 옵션으로 참고문헌 자동 첨부 가능.

**Plan B (실측 결과가 스케치와 다르면)**: Visualization API 호출은 유지하되, 직접 만든 경량 커스텀 컴포넌트(막대+리스트)를 프론트에서 별도로 그리고, Visualization API 결과는 보조 화면으로만 노출하는 대안도 고려한다.

## API 매핑 요약
6개를 억지로 다 쓰지 않고, 역할이 명확한 3~4종만 사용한다:

| 역할 | API |
|---|---|
| 학술·산업 증거를 직접 통제하며 탐색 | Search API (Scholar/Web 분리 — 확인됨) |
| 상위 갭의 근거를 인용과 함께 종합 / 반증 탐색 | Search Agent |
| 논쟁적이거나 복잡한 후보만 심층 검증 | Deep Research (조건부) |
| 결과 시각화 | Visualization API |

## 서프라이즈 태스크 / 잘못된 입력 대응표

| 입력 유형 | 문제 | 대응 |
|---|---|---|
| 너무 광범위 (`"AI"`) | 갭이 무한대 | Scope Calibrator가 하위주제로 자동 분해 |
| 너무 니치 | 검색 결과 희소 | "충분한 근거 확보 못함" 정직하게 보고, 억지 갭 생성 안 함 |
| 존재하지 않는/가짜 분야 | 검색 결과 0 | "분야 자체 확인 안 됨"으로 조기 종료 |
| 이미 완전히 산업화된 분야 | 갭 없음 | "적용 갭 없음, 오히려 과잉적용" 판정 — 이것도 정직한 결과로 취급 |
| Deep Research 승급했는데 타임아웃 | 응답 지연 | 강등 로직으로 잠정 결론 + 확신도 표시하고 진행 |
