## 1. 전체 구현 방향

Bridge Agent는 연구 주제 하나를 받아 학술 근거와 산업 도입 근거를 대조한다. 구현의 핵심은 "검색 결과가 없다"를 곧바로 "현실에 없다"로 바꾸지 않는 것이다. 그래서 파이프라인은 학술 검색, 산업 검색, 구조화 추출, 클러스터 연결, 점수 계산, 반증 검색, 조건부 Deep Research, Visualization 순서로 나뉜다.

## 2. 백엔드 기능

### 2.1 FastAPI 진입점과 JSON 에러 처리

관련 파일: `backend/main.py`, `backend/routes/analyze.py`

FastAPI 서버는 `/api/analyze`, `/api/suggestions`, `/api/stream`, `/api/proxy/{target}`, `/api/demo/run`, `/api/health`를 제공한다. `main.py`에서 전역 예외를 JSON으로 감싸는 이유는 프론트가 항상 `res.json()`을 시도하기 때문이다. 서버가 plain text 500을 반환하면 사용자는 원래 실패 원인이 아니라 JSON 파싱 실패만 보게 된다.

따라서 실패를 숨기지 않되, 실패 형식은 UI가 처리 가능한 JSON으로 통일했다.

### 2.2 Raw API Stream

관련 파일: `backend/events.py`, `backend/routes/stream.py`, `frontend/src/components/RawStream.jsx`, `frontend/src/components/EventLine.jsx`

초기 커밋에서 Raw API Stream을 먼저 만든 이유는 발표 규칙 때문이다. 파이프라인이 잘 돈다는 결과보다 "어떤 API를 왜 호출했는지"를 실시간으로 보여줘야 했다.

구현 방식:

- `emit_event(type, payload, stage, source)`가 전역 이벤트를 만든다.
- 최근 200개 이벤트를 메모리에 보관한다.
- `logs/raw_api_stream.jsonl`에도 기록한다.
- `/api/stream`은 기존 히스토리와 신규 이벤트를 SSE로 흘린다.
- 알 수 없는 Liner SSE 타입도 버리지 않고 그대로 전달한다.
- 프론트는 `tool_call`과 `error`만 색을 다르게 주고 나머지는 원문 JSON으로 보여준다.

이 구조는 Liner 문서에 없는 이벤트가 와도 화면이 깨지지 않게 한다. 실제 커밋에서 `data-quickanswer-queries`, `data-atlas` 같은 미상 이벤트를 모의 라우터에 넣은 것도 이 fallback을 검증하기 위해서다.

### 2.3 API 테스트 프록시

관련 파일: `backend/routes/proxy.py`, `frontend/src/components/ApiTester.jsx`

프론트가 OpenAI/Liner 키를 직접 들고 있지 않도록 서버 프록시를 만들었다. 해커톤 중에는 Liner SSE 이벤트 모양과 OpenAI 응답 스키마를 빠르게 확인해야 했기 때문에, 별도 코드를 매번 짜지 않고 dev 화면에서 수동 호출하도록 했다.

프록시도 Raw Stream에 `tool_call`, `tool_result`, `sse_line`, `error`를 남긴다. 그래서 수동 테스트와 실제 파이프라인 호출이 같은 관찰 화면에 찍힌다.

### 2.4 Liner API 클라이언트

관련 파일: `backend/liner_client.py`

Liner 호출은 `LinerClient`에 모았다.

| 메서드 | API | 사용 단계 |
|---|---|---|
| `search_scholar()` | `/api/v1/tools/search/scholar` | 학술 근거 검색 |
| `search_web()` | `/api/v1/tools/search/web` | 산업 도입 사례 검색 |
| `search_agent()` | `/api/v1/agents/search` | 반증 검색 |
| `deep_research()` | `/api/v1/agents/deep-research` | 조건부 심층 검증 |
| `visualize()` | `/api/v1/tools/visualization` | Gap Map 생성 |

Search API는 JSON 응답이고, Search Agent, Deep Research, Visualization은 SSE 응답이다. 그래서 `_search()`와 `_stream_request()`를 분리했다. 인증은 Liner 요구사항에 맞춰 `Authorization: Bearer`가 아니라 `x-api-key`를 사용한다.

SSE 파서는 `data:` 라인만 읽고 `[DONE]`은 종료 신호로 무시한다. 각 SSE payload의 `type`을 그대로 `emit_event()`에 넘기는 이유는 Raw API Stream의 원문성 때문이다.

### 2.5 OpenAI Agents SDK 역할 분리

관련 파일: `backend/openai_agents.py`

OpenAI 호출은 전부 Pydantic 출력 타입을 가진 Agent로 분리했다.

작은 모델 기본값: `OPENAI_SMALL_MODEL` 또는 `gpt-4o-mini`  
큰 모델 기본값: `OPENAI_LARGE_MODEL` 또는 `gpt-4o`

작은 모델이 맡는 일:

- 입력 사전 검사
- Scholar 쿼리 생성
- 학술 용어를 산업 검색어로 변환
- 학술 검색 결과에서 증거 레코드 추출
- 산업 검색 결과에서 도입 레코드 추출

큰 모델이 맡는 일:

- 주제 범위 판정
- 연구 클러스터와 산업 클러스터의 의미상 연결 차원 판정
- Deep Research 보고서 검토

최종 점수와 label은 LLM이 정하지 않는다. LLM은 "이 결과가 재현연구인가", "이 산업 문서가 실제 운영을 말하는가", "두 클러스터가 같은 사용 사례인가" 같은 이산 신호를 추출한다. 점수 계산과 최종 판정은 `evidence_logic.py`가 담당한다.

이 분리는 점수 설명 가능성을 위해 도입했다. LLM이 "82점"이라고 쓰면 발표 중 왜 82인지 설명하기 어렵지만, 코드가 `독립 출처 수`, `재현 여부`, `현장 검증`, `도입 단계`를 가중합하면 근거를 바로 보여줄 수 있다.

### 2.6 입력 사전 검사와 추천어

관련 파일: `backend/routes/analyze.py`, `backend/openai_agents.py`, `frontend/src/components/UserView.jsx`

`/api/suggestions`와 `/api/analyze` 시작부는 같은 preflight를 사용한다. 너무 넓은 입력이나 복구 불가능한 오타를 전체 파이프라인에 넣으면 Liner와 OpenAI 비용을 쓰고도 모호한 결과가 나온다.

상태는 네 가지다.

| 상태 | 의미 | 처리 |
|---|---|---|
| `ready` | 바로 분석 가능 | 추천어와 함께 진행 가능 |
| `auto_corrected` | 오타 또는 제품 아이디어를 기술명으로 보정 | 보정 주제로 분석 |
| `needs_calibration` | 너무 넓거나 좁음 | 추천 검색어를 보여주고 파이프라인 중단 |
| `rejected` | 가짜 분야, 무의미 문자열, 복구 불가 오타 | "검색어를 다시 확인해 주세요." 반환 |

`AI`, `LLM`, `RAG`, `GNN`, `diffusion model`처럼 모델이 ready로 잘못 보낼 수 있는 넓은 주제는 코드의 `_BROAD_TOPIC_RECOMMENDATIONS`가 다시 보정한다. `cb24f8b`의 넓은 주제 보정 커밋은 이 문제를 해결하기 위한 것이다.

### 2.7 분석 라우트와 빠른 모드

관련 파일: `backend/routes/analyze.py`, `backend/runtime_config.py`, `frontend/src/components/UserView.jsx`

`/api/analyze`는 `fast_mode`에 따라 timeout 전략을 바꾼다.

- `fast_mode=true`: 단계별 시간 제한을 적용한다.
- `fast_mode=false`: `RuntimeConfig(disable_timeouts=True)`로 전체 분석을 더 길게 기다릴 수 있다.

이 설계는 발표용과 탐색용을 나누기 위해 추가됐다. 발표 중에는 55초 기본 예산 안에서 부분 결과라도 반환해야 하고, 팀 내부 확인 중에는 시간 제한 없이 더 완전한 결과를 보고 싶다.

`ResearchPipeline.last_partial_result`는 이 목적을 위해 있다. 학술/산업 근거와 1차 점수를 계산한 뒤, 반증 검색 뒤, 최종 정리 전마다 현재까지의 결과를 저장한다. 전체 deadline이 끝나면 빈 에러 대신 마지막 부분 결과를 반환한다.

## 3. 파이프라인 기능

### 3.1 Scope Calibrator

관련 파일: `backend/agent_pipeline.py`, `backend/openai_agents.py`

너무 넓은 입력은 갭 후보가 무한히 많고, 너무 좁은 입력은 검색 결과가 희박하다. 그래서 첫 단계에서 큰 모델이 범위를 판정한다.

- `broad`: 대표 하위 주제로 좁힌다.
- `focused`: 그대로 진행한다.
- `niche`: 인접한 상위 개념을 선택한다.
- `unconfirmed`: 분야 자체가 확인되지 않으면 조기 종료한다.

시간 예산을 넘기면 원문 주제를 대표 범위로 사용한다. 라이브 데모에서는 "스코프 조정 실패"보다 "분석 자체가 멈춤"이 더 나쁘기 때문이다.

### 3.2 Scholar Scout

관련 파일: `backend/agent_pipeline.py`, `backend/liner_client.py`

학술 단계는 `scholar_query_generator`가 만든 쿼리로 Liner Scholar Search를 호출한다. 초기에는 여러 하위 주제를 병렬 검색했지만, 현재 코드는 대표 주제 1개만 학술 쿼리로 사용한다. 이유는 429와 관련 없는 결과 유입을 줄이기 위해서다.

검색 결과는 `query_family=academic`으로 태깅하고, 이후 학술 증거 추출과 클러스터링의 입력이 된다.

### 3.3 Vocabulary Bridge

관련 파일: `backend/openai_agents.py`, `backend/agent_pipeline.py`

학술 용어를 그대로 산업 검색어로 쓰면 오판이 생긴다. 예를 들어 논문은 formal method name을 쓰지만 산업은 제품명, 오픈소스명, 업무 기능명을 쓴다. 그래서 학술 결과를 바탕으로 `technology`, `use_case`, `context` 세 가족의 검색어를 만든다.

현재 adoption query 생성은 다음 순서로 조합한다.

- 한국어 입력이면 `산업 적용 사례`, `상용 서비스`, `현장 적용` 같은 한국어 질의를 먼저 만든다.
- 기술+사용 사례, 기술+환경, 사용 사례+환경 조합으로 영어 질의를 만든다.
- 검색어가 없으면 원문 term 기반 fallback을 쓴다.
- `RuntimeConfig.max_adoption_queries` 기본값인 3개까지만 사용한다.

한국어 질의를 먼저 넣은 것은 현재 작업트리의 변경이다. 한국어 주제에서 산업 도입 사례가 한국어 기사, 공공기관 보도자료, 기업 사례로 더 잘 잡히는 경우가 많기 때문이다.

### 3.4 Adoption Scout

관련 파일: `backend/agent_pipeline.py`, `backend/liner_client.py`

Adoption Scout는 Liner Web Search를 사용한다. Scholar와 Web을 분리한 이유는 학술 성숙도와 산업 도입 증거를 서로 다른 근거 집합으로 계산하기 위해서다.

각 검색 결과에는 query family가 붙는다.

- `technology+use_case`
- `technology+context`
- `use_case+context`
- `technology`
- `manual`

이 family 수는 Coverage Confidence의 `query_coverage` 계산에 들어간다.

### 3.5 증거 추출

관련 파일: `backend/openai_agents.py`, `backend/agent_pipeline.py`, `backend/evidence_models.py`

검색 결과 하나를 그대로 점수화하지 않고 EvidenceRecord로 바꾼다.

학술 추출 조건:

- 관련 없는 결과는 생략한다.
- `extraction_confidence < 0.55`는 제외한다.
- `technology_canonical`과 `evidence_span`이 있어야 한다.
- 재현연구, 종합연구, 현실 검증, 결과 방향을 보수적으로 추출한다.

산업 추출 조건:

- 실제 사용, 파일럿, 제한 운영, production, 중단, 거절, 제거, 금지를 직접 말하는 문서만 남긴다.
- 계획, 관심, 호환, 채용공고만 있으면 제외한다.
- 검색 결과가 없다는 사실을 `does_not_use`로 바꾸지 않는다.
- 제품 통합과 최종 사용 조직의 업무 도입을 구분한다.
- 한국어 결과에서는 도입, 구축, 운영, 현장 적용, 상용화, 납품, 실증, 시범 운영 같은 표현을 실제 사용 신호로 본다.

추출 대상이 많으면 상위 `MAX_EXTRACTION_ITEMS`개만 구조화한다. 기본값은 24개다. 이 제한은 프롬프트 비용과 응답 시간을 통제하기 위해 있다.

### 3.6 클러스터링

관련 파일: `backend/evidence_logic.py`, `backend/evidence_models.py`

증거 레코드는 바로 비교하지 않고 클러스터로 묶는다.

ResearchCluster 키:

```text
technology_canonical
+ use_case_canonical
+ context_canonical
+ expected_value_canonical
```

AdoptionCluster 키:

```text
subject_canonical
+ technology_canonical
+ use_case_canonical
+ context_canonical
+ project_name 또는 deployment_unit
```

연구 클러스터는 `evidence_maturity`와 논문 수 기준 상위 5개를 사용한다. 산업 클러스터는 도입 단계와 독립 출처 수 기준 상위 5개를 사용한다. 상한을 둔 이유는 라이브 데모에서 모든 조합을 LLM에 보내면 연결 판단 비용과 시간이 급격히 늘기 때문이다.

### 3.7 클러스터 연결

관련 파일: `backend/openai_agents.py`, `backend/evidence_logic.py`, `backend/agent_pipeline.py`

큰 모델은 연구 클러스터와 산업 클러스터를 네 차원으로 비교한다.

| 차원 | 가중치 | 값 |
|---|---:|---|
| technology | 0.40 | 0.0, 0.5, 1.0 |
| use_case | 0.30 | 0.0, 0.5, 1.0 |
| context | 0.20 | 0.0, 0.5, 1.0 |
| expected_value | 0.10 | 0.0, 0.5, 1.0 |

모델은 차원별 값과 설명만 반환한다. 코드가 아래 식으로 유사도를 계산한다.

```text
link_similarity =
  technology_match * 0.40
+ use_case_match * 0.30
+ context_match * 0.20
+ expected_value_match * 0.10
```

연결 타입은 코드가 정한다.

| 타입 | 조건 |
|---|---|
| `direct` | `relation=uses`, technology=1.0, use_case=1.0, similarity >= 0.80 |
| `partial` | `relation=uses`, similarity >= 0.45 |
| `blocked` | `relation=does_not_use`, similarity >= 0.45 |
| `unlinked` | 위 조건을 만족하지 않음 |

`direct`에 technology와 use_case 완전 일치를 요구하는 이유는 추천, 검색, 큐레이션 같은 인접 사용 사례가 실제 도입 점수를 과하게 올리는 문제를 막기 위해서다. `505e8d2`, `d94c707` 이후의 판정 보정도 이 방향이다.

### 3.8 반증 검색

관련 파일: `backend/agent_pipeline.py`, `backend/liner_client.py`

갭을 선언하기 전에 반대 증거를 찾는다. 질문은 "같은 기술, 같은 사용 사례, 같은 환경에서 이미 production으로 쓰이고 있다는 직접 증거"를 찾도록 만든다.

반증 검색 실행 조건:

- 도입 증거와 중단 증거가 같이 있다.
- 연결된 도입 근거가 없고 blocked만 있다.
- 산업 도입 후보는 있지만 상위 연구 클러스터와 연결되지 않는다.
- 산업 도입 레코드가 아예 없다.

1차 산업 검색에서 이미 연결 가능한 도입 근거가 있으면 반증 검색을 생략한다. 이때 Coverage Confidence의 adversarial 점수는 20점으로 처리한다. "이미 도입 증거가 있는데 굳이 반증 검색을 돌리지 않았다"는 상황을 검색 부족으로 벌점 주지 않기 위해서다.

### 3.9 조건부 Deep Research

관련 파일: `backend/agent_pipeline.py`, `backend/evidence_logic.py`, `backend/liner_client.py`

Deep Research는 항상 호출하지 않는다. 비용과 시간이 크기 때문에 코드 계산이 필요하다고 판단할 때만 승격한다.

승격 조건:

- 학술 반대 근거가 있고 `evidence_maturity >= 60`
- 직접 도입과 중단 증거가 동시에 존재
- `gap_priority >= 45`인데 `coverage_confidence < 70`
- 우선순위가 높은 후보인데 blocked 원인이 명확하지 않음

타임아웃이 나면 Search 근거로 잠정 결론을 유지하고, Deep Research 상태를 `timeout`으로 반환한다. 완료되면 Deep Research 보고서를 다시 OpenAI reviewer가 읽고 `confirmed_barriers`, `inferred_barriers`, `explicit_outcome_mismatch`만 추출한다.

## 4. 계산 로직

### 4.1 정규화와 중복 제거

관련 파일: `backend/evidence_logic.py`

점수 계산 전에 같은 근거가 중복으로 세지 않도록 정규화한다.

- `canonical_url()`은 URL scheme과 host를 소문자로 만들고, trailing slash와 `utm_source`, `utm_campaign`, `utm_medium`, `ref`, `fbclid`를 제거한다.
- `normalize_text()`는 대소문자, 회사 법인 접미사, 불필요한 문자를 정리한다.
- `source_id()`는 DOI가 있으면 DOI를 우선 사용하고, 없으면 canonical URL, 그것도 없으면 제목과 날짜로 stable hash를 만든다.
- `deduplicate_records()`는 `source_id + evidence_span` 조합으로 중복 레코드를 제거한다.

이 구조는 같은 문서가 여러 검색어에서 반복 노출되어도 점수가 부풀지 않도록 하기 위한 것이다.

### 4.2 Evidence Maturity

관련 파일: `backend/scoring_config.py`, `backend/evidence_logic.py`

Evidence Maturity는 연구 클러스터 하나가 얼마나 성숙한 적용 주장인지 나타낸다. 만점은 100점이다.

계산식:

```text
breadth     = min(unique_paper_count, 5) / 5 * 30
replication = min(replication_count, 2) / 2 * 15
synthesis   = min(synthesis_count, 1) * 15
real_world  = min(real_world_count, 2) / 2 * 20

classified = supports_count + mixed_count + contradicts_count
direction =
  0                                                        if classified == 0
  (supports_count + 0.5 * mixed_count) / classified * 20   otherwise

evidence_maturity = round(breadth + replication + synthesis + real_world + direction)
```

가중치 의미:

| 신호 | 최대점 | 이유 |
|---|---:|---|
| 독립 학술 출처 수 | 30 | 논문 1건만으로 성숙하다고 보기 어렵다. 5건에서 상한을 둔다. |
| 재현연구 | 15 | 독립 재검증은 연구 주장 안정성을 올린다. 2건에서 상한을 둔다. |
| 종합연구 | 15 | systematic review, meta-analysis는 근거 체계를 강화한다. 1건이면 충분한 신호로 본다. |
| 현실 환경 검증 | 20 | 실제 기관, 사용자, 업무 흐름에서 검증된 연구를 높게 본다. 2건에서 상한을 둔다. |
| 결과 방향 | 20 | supports는 1점, mixed는 0.5점, contradicts는 0점처럼 반영한다. unclear는 분모에서 제외한다. |

예시:

```text
unique_paper_count = 4
replication_count = 1
synthesis_count = 0
real_world_count = 1
supports_count = 3
mixed_count = 1
contradicts_count = 0

breadth = 4/5*30 = 24
replication = 1/2*15 = 7.5
synthesis = 0
real_world = 1/2*20 = 10
direction = (3 + 0.5*1) / 4 * 20 = 17.5
total = round(59)
```

이 점수는 "연구가 참이다"가 아니라 "검색된 연구 근거가 얼마나 성숙한가"다.

### 4.3 Link Similarity와 link_type

클러스터 연결은 네 차원 가중합이다.

```text
technology 40%
use_case 30%
context 20%
expected_value 10%
```

`direct` 판정에는 두 가지 추가 조건이 있다.

1. 산업 레코드의 최신 relation이 `uses`여야 한다.
2. technology와 use_case가 모두 1.0이어야 한다.

그래서 아래와 같은 케이스는 similarity가 높아도 직접 도입으로 세지 않는다.

- 기술은 같지만 사용 사례가 추천/검색처럼 인접 기능인 경우
- 사용 사례는 같지만 산업에서는 다른 기술로 푼 경우
- 연구는 병원 다기관 검증인데 산업 사례는 일반 SaaS 내부 사용인 경우

이 보수적 판정은 "이미 완전히 산업화된 분야는 no_gap으로 뒤집되, 인접 사례만으로 gap이 해소됐다고 말하지 않는다"는 요구를 만족하기 위한 것이다.

### 4.4 Adoption Evidence

관련 파일: `backend/scoring_config.py`, `backend/evidence_logic.py`

Adoption Evidence는 같은 연구 클러스터와 연결된 산업 도입 증거가 얼마나 강한지 나타낸다.

1단계: 도입 사건별 기본점

| usage_context | link_type | production | limited_deployment | pilot | unknown |
|---|---|---:|---:|---:|---:|
| `end_user_use` | direct | 45 | 25 | 12 | 8 |
| `end_user_use` | partial | 25 | 14 | 7 | 4 |
| `vendor_internal_use` | direct | 20 | 12 | 7 | 4 |
| `vendor_internal_use` | partial | 10 | 6 | 3 | 2 |

`vendor_product_integration`은 항상 4점이다. 제품에 기능이 있다는 사실은 도입 신호지만, 고객 업무에 실제로 쓰인 것과 같게 볼 수 없어서 낮게 둔다.

2단계: 조직별 집계

같은 조직이 여러 클러스터로 잡히면 가장 강한 증거는 100%, 두 번째 증거는 50%, 세 번째 이후는 0%로 계산한다.

```text
organization_score =
  min(first_score * 1.0 + second_score * 0.5, ORGANIZATION_MAX)

ORGANIZATION_MAX = 30
```

조직 상한 30점을 둔 이유는 한 회사의 보도자료 여러 건이 전체 adoption 점수를 지배하지 않게 하기 위해서다.

3단계: 상위 조직 합산

```text
base_score = min(sum(top_3_organization_scores), BASE_ADOPTION_MAX)
BASE_ADOPTION_MAX = 75
```

상위 3개 조직만 합산한다. 라이브 검색 결과에서는 특정 벤더나 특정 기관 자료가 반복될 수 있으므로, 넓은 산업 채택은 조직 수와 final-user 폭으로 따로 본다.

4단계: 최종 사용자 폭 보너스

```text
final_user_orgs = end_user_use 조직 수
breadth_bonus =
  0  if 0~1개
  8  if 2개
  15 if 3개
  20 if 4개
  25 if 5개 이상
```

최종 계산:

```text
adoption_evidence = min(round(base_score + breadth_bonus), 100)
```

현재 작업트리에는 partial-only 보정이 들어가 있다.

```text
if direct link가 하나도 없으면:
  adoption_evidence = min(adoption_evidence, gap_max_adoption)

gap_max_adoption = 30
```

부분 연결은 인접 산업 사례로는 유용하지만, "같은 연구 적용이 이미 산업에 도입됐다"는 직접 증거는 아니다. 그래서 partial만 있을 때는 점수가 30을 넘지 않게 막는다.

### 4.5 Coverage Confidence

관련 파일: `backend/evidence_logic.py`

Coverage Confidence는 "직접 도입 연결이 없다"는 결론을 내릴 만큼 검색이 충분했는지 나타낸다.

계산식:

```text
scholar_coverage = min(unique_academic_sources / 5, 1.0) * 20
web_coverage     = min(unique_web_sources / 8, 1.0) * 20
query_coverage   = min(query_family_count, 3) / 3 * 15
mapping_score    = clamp(mapping_confidence, 0, 1) * 15
extraction_score = 0 if total_relevant_results == 0
                   else structured_record_count / total_relevant_results * 10

adversarial_score =
  20 if adversarial_skipped_with_adoption
  0  if adversarial not performed
  5  if adversarial timed out
  12 if adversarial result count == 0
  16 if adversarial result count == 1
  20 if adversarial result count >= 2

coverage_confidence = round(sum(all signals))
```

가중치 의미:

| 신호 | 최대점 | 이유 |
|---|---:|---|
| 학술 출처 폭 | 20 | 연구 쪽 근거가 넓게 확인됐는지 본다. |
| 웹 출처 폭 | 20 | 산업 쪽 검색 범위가 충분했는지 본다. |
| 검색 관점 다양성 | 15 | 기술명, 사용 사례, 환경을 모두 검색했는지 본다. |
| 학술어-산업어 매핑 확신도 | 15 | 용어 변환이 불확실하면 검색 부재 결론도 약해진다. |
| 구조화 성공률 | 10 | 결과는 많지만 추출 가능한 근거가 없으면 신뢰도가 낮다. |
| 반증 검토 | 20 | 갭 선언 전 반대 방향 검색을 했는지 본다. |

### 4.6 Gap Priority

관련 파일: `backend/evidence_logic.py`

Gap Priority는 후보 정렬과 Deep Research 승격 판단에 쓰는 내부 점수다.

```text
gap_priority =
  round(evidence_maturity * (100 - adoption_evidence) / 100 * coverage_confidence / 100)
```

해석:

- 연구 근거가 높을수록 올라간다.
- 산업 도입 증거가 낮을수록 올라간다.
- 검색 커버리지가 높을수록 올라간다.

예시:

```text
evidence_maturity = 80
adoption_evidence = 10
coverage_confidence = 75

gap_priority = round(80 * 0.90 * 0.75) = 54
```

이 값은 사용자에게 핵심 점수로 강조하지 않는다. 사용자는 연구 근거, 도입 증거, 판정 신뢰도를 이해하면 충분하고, priority는 내부 정렬용이다.

### 4.7 gap_type 판정

관련 파일: `backend/evidence_logic.py`

| gap_type | 조건 |
|---|---|
| `no_adoption_link` | direct link가 없고 coverage >= 70 |
| `possible_no_adoption_link` | direct link가 없고 coverage < 70 |
| `stage_gap` | direct 또는 partial 연결은 있지만 pilot/limited_deployment 단계 |
| `context_gap` | 기술과 사용 사례는 관련 있지만 context가 맞지 않음 |
| `technology_substitution` | 같은 사용 사례와 context에서 산업은 다른 기술을 production 사용 |
| `barrier_gap` | `does_not_use` 기반 blocked link 존재 |
| `outcome_gap` | Deep Research review에서 성과 불일치가 직접 확인됨 |

gap_type은 label보다 세부적이다. 예를 들어 label이 `emerging_adoption`이어도 `stage_gap`이 같이 붙을 수 있다.

### 4.8 최종 label 판정

관련 파일: `backend/evidence_logic.py`

현재 label 판정 순서는 다음과 같다.

```text
1. field_not_confirmed
   → unconfirmed_field

2. adoption_evidence >= 60
   또는 direct production 조직 수 >= 2
   → no_gap

3. adoption_evidence > 0
   → emerging_adoption

4. coverage_confidence < 50
   또는 evidence_maturity < 40
   → insufficient_evidence

5. evidence_maturity >= 70
   and adoption_evidence <= 30
   and coverage_confidence >= 70
   → gap_candidate

6. 그 외
   → emerging_adoption
```

이 순서는 의도적이다.

- 이미 도입 증거가 강하면 `no_gap`을 먼저 반환한다.
- adoption evidence가 조금이라도 있으면 "아직 적용되지 않았다"가 아니라 "일부 확인됐다"로 표현한다.
- 연구 근거 또는 검색 커버리지가 약하면 억지 갭을 만들지 않는다.
- 현재 우선순위에서는 `adoption_evidence > 0`이 먼저 `emerging_adoption`으로 잡힌다. 따라서 강한 `gap_candidate`는 연구 성숙도와 커버리지가 충분하면서, 직접/부분 도입 점수로 반영된 연결 증거가 0점인 경우에만 나온다.

`d98b52b`, `505e8d2` 이후 라벨 우선순위를 보정한 이유는 결과 문구와 점수가 모순되는 문제를 줄이기 위해서다.

### 4.9 상위 후보 선택

관련 파일: `backend/agent_pipeline.py`

후보가 여러 개일 때 `_top_analysis()`는 다음 순서로 고른다.

1. `no_gap` 후보가 있으면 adoption evidence가 가장 높은 no_gap 후보
2. 그다음 `emerging_adoption` 후보 중 adoption evidence가 가장 높은 후보
3. 그 외에는 gap priority가 가장 높은 후보

이 선택은 "입력 분야가 이미 산업화된 경우 갭 없음으로 뒤집기"를 위해 중요하다. gap 후보만 찾으려고 정렬하면 이미 도입된 분야에서도 낮은 priority gap을 억지로 보여줄 수 있다.

## 5. 프론트엔드 기능

### 5.1 화면 라우팅

관련 파일: `frontend/src/App.jsx`

URL로 화면을 나눈다.

- `?view=user` 또는 기본값: 실제 사용자 화면
- `?view=stream` 또는 `?clean=1`: Raw API Stream 전용 세컨드 화면
- `?view=dev`: Raw Stream, API 테스트, Gap Map 탭이 있는 개발 화면

발표 중에는 사용자 화면과 Raw Stream 화면을 분리해 띄울 수 있다. 이것은 결과 화면과 API 원문 로그가 서로 방해하지 않게 하기 위한 구조다.

### 5.2 사용자 입력과 실시간 추천어

관련 파일: `frontend/src/components/UserView.jsx`

사용자가 타이핑을 멈추고 350ms가 지나면 `/api/suggestions`를 호출한다. 이미 나간 요청은 `AbortController`로 취소한다. 이 race condition 처리는 `adbbf08`, `3e4fa82` 계열 커밋에서 보정됐다.

설계 이유:

- 오타나 너무 넓은 주제를 제출 전에 알려준다.
- 결과를 보고 있는 상태에서도 새 입력의 추천어는 뜨게 한다.
- 오래된 추천어 응답이 뒤늦게 돌아와 현재 입력 상태를 덮어쓰지 않게 한다.

추천 칩 동작은 두 가지다.

- 사전 검사 결과 화면의 추천어: 클릭하면 바로 분석을 실행한다.
- 타이핑 중 실시간 추천어: 클릭하면 입력창만 채운다.

### 5.3 빠른 모드

관련 파일: `frontend/src/components/UserView.jsx`, `backend/routes/analyze.py`, `backend/runtime_config.py`

빠른 모드는 입력창 옆 번개 아이콘으로 제공한다.

- 켜짐: 단계별 timeout을 적용한다.
- 꺼짐: timeout을 끄고 더 오래 분석한다.

발표 시에는 빠른 모드가 유리하다. 외부 API가 늦어도 부분 결과를 반환하기 때문이다. 내부 리허설이나 디버깅에서는 끄고 더 긴 결과를 볼 수 있다.

### 5.4 진행 상태 표시

관련 파일: `frontend/src/components/UserView.jsx`

프론트는 `/api/stream`을 같이 구독해서 최신 `event.stage`를 사용자 문구로 바꿔 보여준다.

예:

- `scholar_scout` → 학술 근거 검색하는 중
- `adoption_scout` → 산업 도입 사례 검색하는 중
- `cluster_linkage` → 학술과 산업 사례를 연결하는 중
- `score_calculation` → 점수와 갭 유형을 계산하는 중

`tool_call` 이벤트에 Liner Search query가 있으면 실제 검색어도 보여준다. 추상적 로딩 문구보다 "어떤 검색어로 찾는지"가 신뢰를 더 주기 때문이다.

### 5.5 결과 라벨과 점수 카드

관련 파일: `frontend/src/components/UserView.jsx`

백엔드 label은 사용자 문구로 바꾼다.

| label | 화면 문구 |
|---|---|
| `gap_candidate` | 아직 산업 현장에 적용되지 않았습니다 |
| `emerging_adoption` | 산업 적용이 일부 확인됐습니다 |
| `insufficient_evidence` | 판단할 근거가 아직 부족합니다 |
| `unconfirmed_field` | 입력한 분야를 다시 확인해주세요 |
| `no_gap` | 이미 산업에 도입되어 있습니다 |

점수는 0~100 값을 퍼센트로 보여준다.

- 검색된 연구 근거는 얼마나 충분한가: `evidence_maturity`
- 실제로 쓰이고 있나: `adoption_evidence`
- 판정 신뢰도: `coverage_confidence`

색상 강도는 낮음, 중간, 높음 세 단계다. 점수 자체보다 상대적 강도가 바로 읽히도록 하기 위해서다.

### 5.6 계산 근거와 연결 구조

관련 파일: `frontend/src/components/UserView.jsx`

결과 화면은 `rationale`, `score_breakdown`, `gap_types`, `links`를 보여준다.

- `계산 근거`: 점수별 total과 rationale
- `주요 갭`: gap_type을 사용자 문구로 변환
- `연구·산업 연결`: direct, partial, blocked, unlinked와 유사도
- `연계된 근거`: 실제로 맞아떨어진 지점
- `연계 안 된 부분`: 갭으로 볼 수 있는 지점
- `추가로 연계될 여지`: 후보 연결

단순 링크 목록보다 "무엇이 연결됐고, 무엇이 끊겼고, 무엇을 더 확인해야 하는지"를 보여주는 것이 제품 컨셉에 맞기 때문에 3갈래 구조로 바꿨다.

### 5.7 근거 목록과 페이지네이션

관련 파일: `frontend/src/components/UserView.jsx`

학술 근거와 산업 검색 결과는 검색엔진 결과처럼 보여준다.

- 제목 링크
- 출처 도메인
- snippet
- 학술 근거는 citation count가 있으면 표시

5개씩 페이지로 나누는 이유는 결과 화면이 갑자기 길어지지 않게 하기 위해서다. 더보기 토글에서 페이지네이션으로 바뀐 커밋도 같은 UX 안정화 목적이다.

### 5.8 Gap Map

관련 파일: `frontend/src/components/GapMap.jsx`, `backend/liner_client.py`, `backend/agent_pipeline.py`

Visualization API의 `data-atlas` 이벤트에서 `atlasArtifact.html`을 받아 iframe `srcDoc`으로 렌더링한다. 직접 HTML을 해석하지 않고 Liner가 준 artifact를 그대로 보여준다.

iframe 높이는 내부 문서의 scrollHeight와 실제 요소 bottom을 재고, `ResizeObserver`로 다시 맞춘다. Liner artifact 내부에 스크롤이 생기거나 잘리는 문제를 줄이기 위해서다.

### 5.9 테마와 화면 안정화

관련 파일: `frontend/src/index.css`, `frontend/src/App.css`, `frontend/src/components/UserView.jsx`

후반 커밋에서 다크 모드를 기본으로 두고 라이트 모드 토글을 추가했다. 선택값은 `localStorage`에 저장하고 `<html data-theme>` 토큰으로 CSS 변수를 바꾼다.

레이아웃 관련 커밋은 대부분 진행 중 화면이 흔들리거나, 결과를 본 뒤 입력을 수정했을 때 상태가 꼬이는 문제를 줄이기 위한 것이다.

## 6. 응답 데이터 구조

`/api/analyze`의 완료 응답은 다음 범주로 나뉜다.

| 범주 | 필드 |
|---|---|
| 입력과 사전 검사 | `input_topic`, `topic`, `preflight`, `recommendations` |
| 쿼리 | `queries.scholar`, `queries.adoption`, `queries.counter`, `scholar_query_generation`, `vocabulary` |
| 판정 | `scores`, `label`, `gap_types`, `rationale`, `analysis_status`, `partial_reason` |
| 구조화 근거 | `academic_evidence`, `adoption_evidence`, `research_clusters`, `adoption_clusters`, `links` |
| 후보 | `gap_candidate`, `gap_candidates`, `candidate_connections` |
| 설명 | `connected_points`, `gap_points`, `potential_points`, `opportunity_suggestions` |
| 원본 검색 결과 | `scholar`, `adoption`, `evidence`, `counter_evidence` |
| 외부 API 상태 | `deep_research`, `visualization`, `timing` |

프론트가 원본 검색 결과와 구조화 결과를 모두 받는 이유는 데모 상황마다 보여줄 정보가 다르기 때문이다. 사용자는 요약 라벨과 근거 목록을 보고, 발표자는 Raw Stream과 구조화 JSON으로 판정 과정을 설명할 수 있다.

## 7. 구현상 중요한 선택

### 7.1 LLM이 점수를 직접 만들지 않는다

초기 기획의 Gap Candidate Generator는 LLM이 점수까지 낼 수 있는 구조였지만, 실제 구현은 증거 구조화와 코드 계산으로 바뀌었다. 이유는 세 가지다.

- 같은 입력에서 점수가 흔들리면 발표 중 설명이 어렵다.
- "관련 논문이 많은데 adoption 점수 3점" 같은 모순을 막아야 했다.
- 커밋 후반에 라벨과 UI 문구가 점수에 의존하게 되면서 결정론적 계산이 더 중요해졌다.

### 7.2 Deep Research는 기본 경로가 아니다

Deep Research는 비용과 시간이 큰 단계라 조건부로만 호출한다. 1차 Search와 반증 검색으로 충분하면 건너뛴다. 이 설계는 "최소 자원으로 최대 검토"라는 발표 프레이밍과도 맞다.

### 7.3 partial link는 기회 신호이지 직접 도입이 아니다

부분 연결은 product opportunity나 추가 검증 후보를 만드는 데 중요하다. 그러나 no_gap 판정에 쓰면 인접 사례가 직접 도입처럼 부풀 수 있다. 그래서 direct 조건을 강화하고, partial-only adoption score는 30점으로 제한했다.

### 7.4 실패를 사용자에게 숨기지 않는다

타임아웃, provider error, SSE data-error는 Raw Stream과 응답 상태에 남긴다. 단, 사용자가 볼 수 있는 결과가 하나도 없으면 데모가 중단되므로, 가능한 경우 부분 결과를 반환한다.

### 7.5 UI는 결과보다 판정 근거를 먼저 읽게 한다

결과 화면은 라벨, 세 점수, 주요 갭, 계산 근거, 연결 구조, 원문 근거 순서다. 이 순서는 "결론 → 숫자 → 왜 그런지 → 원자료"로 읽히게 하기 위한 것이다.

## 8. 현재 한계와 발표 시 설명 방식

- 점수 가중치와 임계값은 과학적으로 검증된 값이 아니라 해커톤 MVP 기본값이다. 그래서 `scoring_config.py`로 분리했다.
- 공개 검색에서 확인되지 않은 도입은 실제 부재가 아니다. 결과 문구는 "현재 검색 범위에서 확인하지 못했다"로 말해야 한다.
- 한국어 산업 자료는 제목과 snippet만으로 도입 단계를 정확히 판단하기 어렵다. 그래서 adoption extractor는 production을 보수적으로 판정한다.
- Visualization API artifact는 Liner가 생성한 HTML이므로 우리가 완전히 원하는 레이아웃으로 통제하지 않는다. 핵심 판정 UI는 자체 컴포넌트가 담당한다.
- 부분 결과는 완성 결과보다 신뢰도가 낮다. 그래서 `analysis_status=partial`과 `partial_reason`을 반드시 보여준다.

발표에서는 다음 문장으로 정리하면 된다.

```text
Bridge Agent는 학술 검색 결과와 산업 검색 결과를 바로 점수 차이로 비교하지 않습니다.
먼저 근거를 구조화하고, 연구 적용 단위와 산업 도입 사건을 클러스터로 묶은 뒤,
기술·사용 사례·환경·기대 효과 네 차원에서 연결 여부를 계산합니다.
그래서 이미 도입된 분야는 no_gap으로 뒤집고, 근거가 부족하면 gap_candidate를 만들지 않습니다.
```
