# AGENT:24 — 실전 파이프라인 전환계획

기준일: 2026.08.01
목적: 현재 모의 데모/초기 백엔드에서 발표 가능한 실전 파이프라인으로 전환하기 위해 남은 작업을 구현 순서와 완료 조건까지 고정한다.

관련 문서: `02_파이프라인_스펙.md`(목표 구조) · `03_실행계획.md`(시간/역할) · `README.md`(실행 방법)

현재 담당 범위:
- 정윤성: 백엔드 라우터, Liner/OpenAI 연동, 파이프라인 오케스트레이션, 백엔드 스모크
- 강지호: 프론트엔드 구현과 화면/디자인

## 1. 현재 상태

### 이미 확인된 것
- Liner Search API 실제 호출 성공:
  - Base URL: `https://platform.liner.com`
  - Web Search: `POST /api/v1/tools/search/web`
  - 인증 헤더: `x-api-key`
  - 요청 body: `query`, `lang`, `country_code`, `date_range`, `max_results`
  - 응답: `requestId`, `results[]`, `totalCount`
- Raw API Stream 구조는 준비됨:
  - `backend/events.py`의 `emit_event()`가 모든 이벤트를 브로드캐스트
  - `GET /api/stream`이 SSE로 최근 히스토리 + 실시간 이벤트 전달
  - unknown event type은 프론트에서 fallback 렌더링 가능
- 데모 라우터는 실제 이벤트 형태를 흉내 내도록 구성됨:
  - `POST /api/demo/run`
  - `note`, `tool_call`, `tool_result`, `text-delta`, `reasoning-delta`, `data-atlas`, `error` 포함
- 초기 실전 라우터/파이프라인 뼈대가 있음:
  - `backend/liner_client.py`: Web/Scholar Search client
  - `backend/agent_pipeline.py`: Scholar Search 후 Web Search 수행
  - `backend/routes/analyze.py`: `POST /api/analyze`

### 지금 빠진 것
- `backend/main.py`에 `analyze.router`가 아직 등록되지 않음.
- `frontend/src/lib/sse.js`가 현재 파일 목록에 없어 프론트 import 확인이 필요함.
- OpenAI Agents SDK 의존성이 `backend/requirements.txt`에 없음.
- Scope Calibrator, Vocabulary Bridge, Gap Candidate Generator가 아직 실제 OpenAI 호출로 붙지 않음.
- Liner Search Agent, Deep Research, Visualization 호출 함수가 아직 `LinerClient`에 없음.
- `/api/analyze`는 현재 전체 6.5단계 파이프라인이 아니라 Scholar/Web Search 초기 흐름만 수행함.

## 2. 최종 목표

입력 1회로 아래 흐름이 끝까지 자동 실행되어야 한다.

1. Scope Calibrator — OpenAI Agents SDK
2. Scholar Scout — Liner Search API Scholar
3. Vocabulary Bridge — OpenAI Agents SDK
4. Adoption Scout — Liner Search API Web
5. Gap Candidate Generator — OpenAI Agents SDK
6. Adversarial Verifier — Liner Search Agent API
7. Conditional Deep Research — Liner Deep Research Agent API, 조건부 호출
8. Gap Map — Liner Visualization API

완료 기준:
- 사용자는 주제만 입력한다. 중간 승인/재질문 없이 파이프라인이 진행된다.
- Raw API Stream에 각 단계의 판단 이유, tool call, tool result, 원본 SSE 이벤트, 실패 이벤트가 노출된다.
- Deep Research는 항상 호출하지 않고, 근거 부족/모순/고임팩트 저확신 조건일 때만 승격된다.
- 결과가 약하면 약하다고 표시한다. 근거가 부족한 주제, 가짜 분야, 이미 산업화된 분야에서 억지 갭을 만들지 않는다.

### 3.2 OpenAI Agents SDK 최소 도입 — 완료
목표: 해커톤 필수 조건인 OpenAI Agents SDK를 실제 파이프라인 판단 단계에 사용한다.

작업:
- `backend/requirements.txt`에 `openai-agents` 추가
- `backend/openai_agents.py` 추가
  - 작은 모델 agent:
    - query generation
    - vocabulary bridge
    - 결과 요약/포맷팅
  - 큰 모델 agent:
    - scope decision
    - gap judgement
    - Deep Research 승격 판단
- 모델명은 환경변수로 분리:
  - `OPENAI_SMALL_MODEL`
  - `OPENAI_LARGE_MODEL`
  - 값이 없으면 코드 안에서 데모용 기본값 사용

구현 기준:

- OpenAI의 token streaming은 필수 아님. 이 프로젝트의 핵심 스트림은 Raw API Stream이므로, 우선 단계 단위 이벤트를 안정적으로 남긴다.

완료 조건:

- `Gap Candidate Generator`가 `evidence_maturity`, `adoption_evidence`, `coverage_confidence`, `gap_label`, `should_deep_research`를 구조화해 반환한다.

구현 확인:

### 3.3 LinerClient를 실전 API 전체로 확장
목표: Liner API 호출 책임을 `LinerClient`에 모으고, 모든 호출이 Raw Stream으로 노출되게 한다.

작업:
- Search 유지:
  - `search_scholar()`
  - `search_web()`
- Search Agent 추가:
  - `search_agent(messages, mode="general" | "scholar", lang="ko", request_id=None)`
  - endpoint: `POST /api/v1/agents/search`
  - 응답은 SSE이므로 라인 단위로 파싱해 원본 `type`을 그대로 `emit_event(type, payload, stage, "liner")`
- Deep Research 추가:
  - `deep_research(messages, lang="ko", timeout_s=25, request_id=None)`
  - endpoint: `POST /api/v1/agents/deep-research`
  - headers: `Accept: text/event-stream`
  - timeout 발생 시 `error` 이벤트를 남기고 지금까지 확보한 Search 근거로 강등
- Visualization 추가:
  - `visualize(query, is_search_context=True, max_results=10, appearance="light")`
  - endpoint: `POST /api/v1/tools/visualization`
  - `data-atlas` 이벤트는 그대로 흘린다. 프론트 `GapMap`이 `atlasArtifact.html`을 받는다.

구현 기준:
- Liner 공식 문서 기준:
  - Search API는 JSON 응답
  - Search Agent, Deep Research, Visualization은 SSE 응답
  - 모든 요청은 `x-api-key`
- SSE 파서는 `data: [DONE]`에서 종료한다.
- 문서에 없는 event type이 와도 필터링하지 않는다.

완료 조건:
- Search Agent 실제 호출 1회가 Raw Stream에 `data-search-references`, `data-search-chunks`, `text-delta`를 남긴다.
- Visualization 실제 호출 1회가 `data-atlas`를 남기고 Gap Map 탭에 iframe이 뜬다.
- Deep Research는 조건이 맞을 때만 호출된다.

### 3.4 ResearchPipeline을 6.5단계로 확장
목표: 현재 Scholar/Web Search 뼈대를 전체 판단 파이프라인으로 바꾼다.

작업 흐름:
1. `run(topic)` 시작 시 `note`: 입력 주제 범위 판정 시작
2. Scope Calibrator:
   - broad: 대표 하위 주제 선택 후 진행
   - niche: 상위/인접 키워드 확장 후 진행
   - fake/unconfirmed: Search 1회 이하로 확인 후 조기 종료
3. Scholar Scout:
   - 각 하위 주제에 Scholar Search
   - 결과 수, citation count, 출처 다양성, 최신성 신호를 수집
4. Vocabulary Bridge:
   - 학술 용어를 산업 검색어로 변환
   - mapping confidence를 Coverage Confidence에 반영
5. Adoption Scout:
   - 산업 동의어 전체로 Web Search
   - 제품문서, 사례연구, 표준, 오픈소스, 채용공고, 조달/보고서 신호군을 카운트
6. Gap Candidate Generator:
   - 세 점수 분리 산출
   - `gap_candidate`, `no_gap`, `insufficient_evidence`, `unconfirmed_field`, `over_adopted` 중 하나로 판정
7. Adversarial Verifier:
   - 상위 후보 1개에 대해 Search Agent로 반증 질의
   - 반증 근거가 강하면 gap label을 낮춘다
8. Conditional Deep Research:
   - `should_deep_research == true`일 때만 호출
   - 타임아웃이면 실패를 노출하고 Search Agent 근거로 잠정 결론
9. Gap Map:
   - 최종 점수와 근거 요약을 Visualization API에 전달
   - 동시에 `/api/analyze` 응답 body에는 구조화된 최종 JSON 반환

완료 조건:
- `/api/analyze` 응답에 최소 다음 필드가 있다:
  - `topic`
  - `scope`
  - `queries`
  - `scores`
  - `label`
  - `rationale`
  - `evidence`
  - `counter_evidence`
  - `deep_research`
  - `visualization`
- Raw Stream만 봐도 각 단계가 왜 다음 단계로 갔는지 설명 가능하다.

### 3.5 모의 데모에서 실전으로 전환
목표: 데모 라우터를 없애기 전에 실전 파이프라인이 같은 화면 계약을 만족하는지 확인한다.

운영 방식:
- 통합 전:
  - 프론트 기본 버튼은 `/api/demo/run`
  - 실전 버튼은 별도 표시
- 실전 스모크 통과 후:
  - 기본 실행 버튼을 `/api/analyze`로 전환
  - `/api/demo/run`은 “모의 파이프라인” 보조 버튼으로 유지
- 발표 직전:
  - 실전 입력이 API/시간 문제로 불안정하면 `/api/demo/run`을 fallback으로 유지
  - 단, 실제 Liner 호출이 Raw Stream에 찍히는 경로를 최소 1회 보여줘야 한다

차이:
- 모의 라우터는 정해진 이벤트와 가짜 점수를 시간차로 흘린다.
- 실전 파이프라인은 입력 주제에 따라 OpenAI 판단, Liner 검색, 조건부 Deep Research, Visualization 결과가 달라진다.
- 프론트는 두 경로를 같은 Raw Stream 이벤트로 받는다. 그래서 화면 구현은 대부분 그대로 둔다.

## 4. API 계약

### `/api/analyze`
요청:
```json
{
  "topic": "온디바이스 sLLM 양자화",
  "max_results": 10
}
```

임시 요청 옵션:
- `scholar_query`: 디버깅용. 없으면 Scope Calibrator 결과 사용.
- `adoption_queries`: 디버깅용. 없으면 Vocabulary Bridge 결과 사용.
- `max_results`: 1~20.

최종 응답:
```json
{
  "topic": "...",
  "scope": {"status": "focused", "selected_topics": ["..."]},
  "queries": {"scholar": ["..."], "adoption": ["..."], "counter": "..."},
  "scores": {
    "evidence_maturity": 82,
    "adoption_evidence": 24,
    "coverage_confidence": 81
  },
  "label": "gap_candidate",
  "rationale": "...",
  "evidence": [],
  "counter_evidence": [],
  "deep_research": {"used": false, "reason": "..."},
  "visualization": {"requested": true, "artifact_received": true}
}
```

### Raw API Stream 이벤트
공통 envelope:
```json
{
  "id": 1,
  "ts": "2026-08-01T00:00:00+00:00",
  "stage": "scholar_scout",
  "source": "liner",
  "type": "tool_call",
  "payload": {}
}
```

필수 이벤트:
- `note`: 왜 이 단계로 넘어가는지 짧은 설명
- `tool_call`: 외부 API 또는 agent 호출 직전
- `tool_result`: JSON 응답 또는 단계 결과
- Liner SSE 원본 타입: `start`, `data-search-references`, `data-search-chunks`, `text-delta`, `reasoning-delta`, `data-atlas`, `finish` 등
- `error` 또는 `data-error`: 실패 사실

금지:
- 실패를 숨기고 성공처럼 반환
- 모르는 SSE 이벤트 타입을 버리기
- Deep Research를 매번 호출
- 점수를 LLM 감으로만 산출

## 5. 점수와 판정 기준

점수는 LLM이 임의 숫자를 쓰는 방식이 아니라, 신호 추출 후 가중합으로 만든다.

### Evidence Maturity
신호:
- 독립 출처 수
- citation count가 있는 논문 수
- 재현/벤치마크/현장실험 여부
- 최근 반례 여부
- 결과 방향 일관성

### Adoption Evidence
신호군:
- 제품문서
- 고객 사례/case study
- 표준/규제/가이드라인
- 오픈소스 구현
- 채용공고/직무기술서
- 조달/산업보고서

### Coverage Confidence
신호:
- Scholar/Web 결과 수
- 학술어→산업어 매핑 신뢰도
- 검색어 다양성
- 반증 질의 수행 여부
- Search Agent citation chunk 확보 여부

### 최종 label
- `gap_candidate`: 연구 근거 높음, 도입 증거 낮음, 커버리지 충분
- `weak_gap_candidate`: 갭 가능성은 있으나 커버리지 부족
- `insufficient_evidence`: 검색 결과가 희소함
- `unconfirmed_field`: 분야 자체가 확인되지 않음
- `no_gap`: 이미 충분히 도입됨
- `over_adopted`: 연구 근거보다 산업 적용이 앞서거나 과잉 적용 신호가 강함

Deep Research 승격 기준은 설정값으로 둔다.
예: `DEEP_RESEARCH_CONFIDENCE_THRESHOLD=0.65`, `DEEP_RESEARCH_TIMEOUT_S=25`, `DEMO_DEEP_RESEARCH_TIMEOUT_S=70`

## 6. 스모크 체크

코드 변경 후 아래 순서만 확인한다. 유닛 테스트/CI는 만들지 않는다.

1. 백엔드 문법 확인:
   - `cd backend`
   - `.venv/bin/python -m py_compile main.py events.py liner_client.py agent_pipeline.py routes/analyze.py`
2. 백엔드 실행:
   - `.venv/bin/uvicorn main:app --host 127.0.0.1 --port 8001`
3. 기본 확인:
   - `GET /api/health`
   - `GET /api/stream`
   - `POST /api/demo/run`
   - `POST /api/analyze`
4. 실제 API 확인:
   - Liner Search Web 1회
   - Liner Search Scholar 1회
   - Liner Search Agent 1회
   - Liner Visualization 1회
   - Deep Research는 승격 조건을 만족하는 안전 입력으로 1회만
5. 프론트 확인:
   - Raw API Stream에 unknown type이 회색 배지로 뜨는지
   - `data-atlas` 수신 시 Gap Map iframe이 뜨는지
   - 실패/timeout이 화면에 그대로 보이는지

## 7. 발표 안정화 기준

발표용 안전 입력은 1~2개만 고정한다.

추천 기준:
- Scholar 결과가 충분히 나오는 주제
- 산업 도입 증거가 완전히 0은 아닌 주제
- Deep Research 승격 또는 스킵 이유를 설명하기 쉬운 주제
- Visualization이 `comparison` 또는 `summary`에 가까운 결과를 내는 주제

발표 중 설명해야 할 로그:
- `Scope Calibrator`: 너무 넓거나 좁은 입력을 어떻게 조정했는지
- `Vocabulary Bridge`: 학술 용어를 산업 용어로 바꾼 이유
- `Adversarial Verifier`: 갭을 선언하기 전에 반대 증거를 찾은 이유
- `Conditional Deep Research`: 호출 또는 스킵 이유
- `Gap Map`: 최종 점수 3개와 신뢰도
